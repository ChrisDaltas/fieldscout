### 1.7 The palette, and why the dark treatment's mechanism is a decision and not a detail

- **The Field Scout palette is LITERAL HEX in `tailwind.config.ts`** — `page: '#e4e5e8'` (`:25`), `ink` (`:26`), `n` (`:27`), `accent` (`:29–34`), `brand` (`:36–41`), `positive`/`negative`/`caution` (`:43–45`), `pos-*` (`:47–56`), `tier-*` (`:58–73`). `src/app/globals.css:14–16` says so in as many words: *"The Field Scout palette proper lives as literal hex in tailwind.config.ts"*.
- **Consequence, and it is the load-bearing fact for DR2.2:** `bg-page` / `border-ink` / `text-n-3` compile to literal colours, so **no CSS-variable override on a wrapper can re-point them**. A room-scoped dark palette is impossible without changing how those tokens resolve.
- **The legacy shadcn layer IS variable-driven** (`tailwind.config.ts:75–110` reading `hsl(var(--…))`, defined at `globals.css:18+`) — so any not-yet-reskinned component inside the room *would* respond to a `:root`-scoped override, while every reskinned one would not. **A half-dark room is the failure mode to design against.**
- **`tailwind.config.ts` declares no `screens` key and no `darkMode` key** (`grep -n 'screens' tailwind.config.ts` → only a comment at `:66`; `grep -n 'darkMode'` → nothing). So the project runs Tailwind's **stock breakpoints** and **`darkMode: 'media'`** — which is exactly why `dark:` must not be used here: it would make the room follow the viewer's OS setting, and §16.1 v2.14 requires the room to be dark for everyone.
- The room's frame paints `bg-page` at `src/app/app/(room)/layout.tsx:28`; the release gate is `(room)/leagues/layout.tsx:18`.

### D205 — The dark room: neutral-layer indirection, room-scoped, and the carve-out's exact shape

1. **The mechanism is forced by §1.7, not chosen for elegance.** The Field Scout palette is literal hex in `tailwind.config.ts` (`:23–73`), so `bg-page` and `border-ink` cannot be re-pointed by any wrapper. Three mechanisms were considered:
   - **(a) Variable indirection over the neutral tokens** — `page`/`ink`/`n-*` (and only those) become `rgb(var(--fs-…) / <alpha-value>)`, defaulting to today's exact values on `:root`, overridden on the room's frame. **CHOSEN.**
   - **(b) A `variant="dark"` prop on every shared component the room mounts.** Rejected: it doubles every shared surface, and — the disqualifying part — a component the room mounts **next month** renders light until somebody remembers. It also multiplies exactly the components CLAUDE.md protects from forking.
   - **(c) A room-scoped CSS override layer re-declaring utility output** (`.fs-room .bg-page { … }`). Rejected: a specificity war with Tailwind's own output, unmaintainable, and invisible to every tool that reads the token layer.
2. **The scope of the re-point is the NEUTRAL layer and nothing else** — page, surface, hairline/border, primary text, muted text. `accent`, `brand`, `positive`/`negative`/`caution`, `pos-*` and `tier-*` keep their app-wide values inside the room. A position badge or a tier chip that means one colour on the Lists page and another in the draft room is two products, and the room is not a separate product. **Consequence, stated so it is not discovered as a surprise:** the design's teal selection (`#00ceb8`) is **not adopted** — selection stays `accent`.
3. **The indirection must be provably a no-op everywhere else.** (a) touches the token layer app-wide, and the risk is a silent whole-app colour drift. The obligation is therefore **an equivalence proof, not an assurance**: the same computed colour, byte-for-byte, on a sampled set of non-room surfaces before and after — and the defaults expressed so that a typo produces a *missing* colour rather than a *slightly different* one. MEMORY's "re-tokenizing is post-launch" caution is respected: this is **indirection over five neutral values**, not the palette re-tune that note defers.
4. **`dark:` is forbidden here, and the reason is mechanical.** `tailwind.config.ts` sets no `darkMode` key, so Tailwind's default `media` strategy applies and `dark:` follows the viewer's OS preference. §16.1 v2.14 requires the room to be dark for **everyone, always**. A `dark:` variant would make the room's appearance depend on a setting nobody in this product chose. **Pin it:** no `dark:` variant anywhere under `src/app/app/(room)/` or `src/components/draft/`.
